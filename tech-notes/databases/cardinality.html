Cardinality

Cardinality is the number of distinct values in a set. The same property that makes a column perfect for an index — every value points at one row — is what makes it lethal as a metric label, where every value becomes a time series held in RAM. Step the animations to see both sides.

Distinct values in a set

Formula

  • selectivity = distinct / rows
  • rows per value = rows / distinct
  • 1.0 means unique, near 0 means one value covers the table

Three meanings

  • column — distinct values in a column
  • table — row count of a set or plan node
  • relationship — 1:1, 1:N, N:M in a data model
SELECT count(*) AS rows,
       count(DISTINCT country) AS distinct_values,
       count(DISTINCT country)::float / count(*) AS selectivity
FROM users;

-- cheaper: the planner already knows
SELECT attname, n_distinct FROM pg_stats WHERE tablename = 'users';
-- positive = absolute count   negative = ratio to row count (-1 = unique)

What counts as high

High cardinality means the distinct-value count is large relative to the row count, or worse, unbounded — it keeps growing as the system runs. Bounded versus unbounded is the distinction that matters, not big versus small.

LOW
2 – 20
MEDIUM
20 – 10k
HIGH
10k – millions
UNBOUNDED
grows forever
boolean, enum, status, environment, region
country, category, http status, handler
city, customer_id, email, IP address
request_id, trace_id, session_id, timestamp, URL

Bounded high cardinality is fine

  • customer_id grows with the business, slowly and predictably
  • Unique keys are maximum cardinality by definition
  • You can size for it, because there is a ceiling

Unbounded cardinality breaks things

  • trace_id mints a new value on every request
  • No ceiling means every sizing assumption downstream is wrong
  • It does not add to your budget, it replaces it

Composite index column order

    
Equality columns first, most selective among them first, ranges and ORDER BY last — everything after the first range column stops being seekable.

    
WHERE tenant_id = ? AND status = ? AND created_at > ?

INDEX (tenant_id, status, created_at)   seek on tenant+status, range scan on time
INDEX (status, created_at, tenant_id)   seek on 5 statuses, then filter everything


    
The low-cardinality escape hatch

    
A skewed low-cardinality column is still worth indexing if you only index the rare value. Low cardinality turned into high selectivity.

    
CREATE INDEX idx_orders_pending ON orders (created_at)
  WHERE status = 'pending';   -- 0.1% of rows, tiny index, cheap to maintain


    
When the planner guesses wrong

    
The planner assumes columns are independent, so it multiplies selectivities. City already implies country, so the estimate comes out far below reality and the plan is built for a row count that never arrives.

    
CREATE STATISTICS city_country (dependencies, ndistinct)
  ON city, country FROM users;
ANALYZE users;

-- skewed high-cardinality column: keep more values in the MCV list
ALTER TABLE events ALTER COLUMN tenant_id SET STATISTICS 1000;

  






  

    

      
Series count is a product, not a sum

      
A time series is identified by the metric name plus every label key and value. Change one value and it is a different series, with its own index entry, chunk buffer and memory. Total series is the cartesian product of all label cardinalities.

      
http_requests_total{method="GET", status="200", handler="/api/users"}   series #1
http_requests_total{method="GET", status="500", handler="/api/users"}   series #2
http_requests_total{method="POST",status="200", handler="/api/users"}   series #3

method(5) × status(8) × handler(40) × pod(20) × region(3) = 96,000
    + user_id(100,000)                                    = 9,600,000,000

      
Adding one unbounded label does not increase your cardinality — it replaces your entire budget with the size of that label's value space.

Churn — the cardinality you forgot to count

    
Series that are created and then go stale. Active series looks reasonable while the index keeps growing, because a stale series stays indexed for the whole retention window and query planning still walks it.

version="a1b2c3d"        new value on every release
container_id             new value on every restart

fix: label the deployment, not the pod
fix: expose build_info as one gauge, not a label on every metric

Finding the offender

    
Never start deleting labels until you know which metric and which label owns the series count. It is almost always one or two.

    
topk(20, count by (__name__)({__name__=~".+"}))    -- series per metric
count(count by (user_id)(http_requests_total))     -- distinct values of one label
prometheus_tsdb_head_series                        -- current head series

promtool tsdb analyze /prometheus                  -- top metrics and labels in a block
GET /api/v1/status/tsdb                            -- top 10 label names and values
