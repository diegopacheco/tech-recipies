Vector Databases

Traditional indexes answer give me row 12345. Vector indexes answer give me the 10 things most like this thing, and they do it by trading a little recall for a lot of speed. Pick an engine, then step the insert and search animations to see the index it actually builds.

      The other algorithms you should be able to name
      
        
        
          
      • HNSW — layered proximity graph, a skip list for high dimensions. Greedy walk from a sparse top layer down to the dense bottom layer. O(log n) search, 95%+ recall, ~2x memory for the edges. The production default.
        • 
          
      • IVF — k-means the space into lists, search only the nprobe nearest lists. Cheap to build, cheap to insert, lower recall at the cell borders, and in 1536 dimensions almost everything is a border.
        • 
          
      • LSH — random hyperplanes as hash bits, similar vectors collide on purpose. Multiple tables raise the odds. Instant build, natural fit for Hamming distance, beaten by HNSW on recall per millisecond.
        • 
          
      • Annoy — a forest of random projection trees, mmap'd from one file so processes share it and the index can exceed RAM. Immutable: adding a vector means rebuilding. Spotify's answer for static catalogs.
        • 
          
      • DiskANN / Vamana — one flat graph tuned so the hops are sequential enough to live on SSD, with a compressed copy in RAM for the distance math. The basis of pgvectorscale and most disk-backed tiers.
        • 
          
      • Quantization (PQ, scalar int8/int4, binary/BBQ) — shrink each dimension before you compare. 4x to 32x less memory, a rescoring pass on the survivors buys back most of the lost recall.

      Numbers to know
      
      
        
        
      • Dimensions: 384 and 768 for open models, 1536 for OpenAI small, 3072 for large.
        • 
        
      • float32 = 4 bytes per dimension. One 1536-dim vector is ~6 KB raw.
        • 
        
      • 1M vectors @ 1536 dims ≈ 6 GB of raw floats, ~12 GB once HNSW edges are in RAM.
        • 
        
      • int8 quantization cuts that 4x, binary/BBQ up to 32x, with a rescore pass to recover recall.
        • 
        
      • Well-tuned p50: 1-5 ms in memory, 10-50 ms over a network, 100-500 ms on object storage.
        • 
        
      • Recall target: 0.95 is fine for almost everything. 0.99 costs real latency or memory.
        • 
        
      • HNSW build over 10M vectors: an hour or more. Plan the rebuild, do not improvise it.
        • 
      
      
    
      
    
      
      
      Decision guide
      
      
        
        
      • Already on Postgres, <10M vectors → pgvector. One query joins similarity with your relational filters and you add zero systems.
        • 
        
      • Already on Elasticsearch, search is the product → kNN there. BM25 + vector with RRF beats either alone.
        • 
        
      • Already on Redis, need sub-millisecond and instant write visibility → Redis Vector Search, if the corpus fits in RAM and you can pay for that RAM.
        • 
        
      • Prototype or a single-node RAG app → Chroma. pip install, no server.
        • 
        
      • Huge cold corpus, cost dominates, sub-second is fine → S3 Vectors.
        • 
        
      • >100M vectors, retrieval is the system, no ops appetite → Pinecone (or Milvus / Qdrant / Weaviate if you want to run it yourself).
        • 
      
      
    
      
    
      
      
      Gotchas that bite in production
      
      
        
        
      • A vector DB is an index, not a source of truth. Authoritative rows live elsewhere; the vector store returns IDs.
        • 
        
      • Embedding drift: change the model and every stored vector is incompatible. Version the model id next to the vector or you will silently search the wrong space.
        • 
        
      • Deletes are soft almost everywhere. Removed vectors still cost memory and traversal until a compaction or rebuild.
        • 
        
      • Filter selectivity decides the plan. Very selective → brute force the survivors. Barely selective → index first. The awkward middle is where the bad plans live.
        • 
        
      • Inserts degrade the graph. Vectors added after the build are worse connected than the ones present during it; recall drifts down between rebuilds.
        • 
        
      • Vector search finds similar, never identical. Exact lookup by id stays a job for a normal index.
