LSM-Tree vs B+Tree

The same operation, side by side. On the left, a B+tree (PostgreSQL / MySQL-InnoDB) updates pages in place with random I/O. On the right, an LSM-tree (Cassandra / RocksDB) only ever appends, buffering in RAM and flushing immutable SSTables. Fire a write or a read and watch both paths light up.

Why the paths differ

Aspect
B+Tree
LSM-Tree
Write
Locate leaf, overwrite page in place; split if full — random I/O, page-level write amplification.
Append to WAL + sorted memtable in RAM; flush whole memtable as an immutable SSTable — sequential I/O.
Read
One path root→internal→leaf, ~3–4 page reads. Low, predictable latency.
Check memtable, then each SSTable newest→oldest; bloom filters skip files that can't hold the key. Higher read amplification.
Delete
Remove the entry from the leaf page immediately.
Write a tombstone; the old value lingers until compaction.
Background
None beyond checkpointing / vacuum.
Compaction merges SSTables, drops overwritten keys and tombstones — costs CPU and can spike tail latency.
Best for
Read-heavy OLTP, range scans over linked leaves.
Write-heavy ingest, logs, metrics, time-series.
Both use a WAL for durability and bloom filters to skip reads. The RUM conjecture: you optimize at most two of Read, Update, Memory — B+tree bets on reads, LSM bets on writes. See the full notes.
