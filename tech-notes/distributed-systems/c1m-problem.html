The problem

C1M is capacity engineering across the entire path.

The C1M problem is the challenge of maintaining 1,000,000 concurrent client connections while preserving useful throughput, bounded latency, and predictable resource use.

Non-blocking I/O from the C10K problem remains essential, but the application is only one layer. The operating system, TLS, network, load balancers, firewalls, connection tracking, and downstream services must all support the target.

Connection lifecycle

Sequence diagram

Core design

Local state, bounded work, measured memory.

01

Shard by CPU core

Assign each connection to one event loop for its lifetime. Core-local state reduces locks, cross-core messages, and cache invalidation.

02

Keep state compact

Allocate large buffers only during activity, reuse them through bounded pools, and avoid a task stack or dependency connection per client.

03

Bound every queue

Cap inbound messages, outbound responses, backend calls, and worker tasks. Slow clients must not retain unlimited memory.

04

Batch carefully

Batch reads, writes, timers, and readiness events to reduce system calls without letting hot clients monopolize an event loop.

05

Group timers

Use timer wheels or coarse buckets for idle deadlines and heartbeats instead of one expensive scheduling structure per connection.

06

Separate capacities

One million sockets cannot mean one million simultaneous backend operations. Admission control protects CPU and dependencies independently.

Failure modes

The steady state is the easy part.

Slow readersOutbound data grows until backpressure, degradation, or disconnection intervenes.
Slow writersPartial requests retain parser state and connection resources for too long.
Reconnect stormsSynchronized TCP and TLS handshakes saturate CPU and accept queues.
Hot shardsUneven activity overloads one event loop while other cores remain available.
Downstream spikesCheap client messages amplify into expensive service or database traffic.

Validation

Test activity, churn, and recovery—not just idle sockets.

  • Ramp gradually to one million established connections.
  • Verify stable memory per connection over time.
  • Mix idle, active, slow-reading, and slow-writing clients.
  • Track tail latency, event-loop delay, fairness, and queue depth.
  • Measure TLS handshakes, packet rate, retransmissions, and drops.
  • Monitor load-balancer and connection-tracking utilization.
  • Remove a host and measure reconnect, redistribution, and recovery.
  • Use multiple load generators when source ports or client resources become the limit.

DAU conversion

The estimate assumes 50 dynamic API requests per DAU per day and a peak-to-average traffic factor of 10. Therefore:

DAU ≈ safe RPS × 86,400 ÷ 50 ÷ 10
DAU ≈ safe RPS × 172.8

What changes the result

  • A database query, remote API, template render, large payload, or synchronous log can reduce RPS by several times.
  • DAU is a product traffic calculation, not a server property. More requests per user or a sharper peak lowers supported DAU directly.
  • Run at least two instances for availability and size the fleet for one-instance loss.
  • Measure p99 latency, CPU, memory, queue depth, errors, and connection churn with the real endpoint before setting capacity.
